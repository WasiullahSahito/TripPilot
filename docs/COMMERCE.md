# Real booking and payment

TripPilot can sell flights, stays and insurance itself. Everything is off until you add keys; with no keys the site keeps linking out to partners.

**Status: written and covered by automated tests that use fake providers. It has NOT been run against live Stripe or Duffel accounts.** Do the checklist below in test mode before taking real money.

## Two payment methods

- **Customers living in Pakistan pay with Safepay** (card, Easypaisa, JazzCash). **Everyone else pays with Stripe.** The default comes from the country of residence in the user's profile; if only one gateway is configured it is used for everyone, and when both are configured the customer can switch in the checkout form.
- Each gateway has its own webhook URL: `/api/commerce/webhook/stripe` and `/api/commerce/webhook/safepay`.
- **The Safepay adapter is UNVERIFIED** (`server/src/integrations/safepay.ts`). It was written without access to Safepay's official API reference. Wrong guesses fail safely (a webhook it does not recognise is ignored, never treated as a payment), but it will probably need small corrections: make a sandbox payment, compare the marked steps with Safepay's docs and with the real webhook (the server log names any field it could not read).
- **Safepay refunds are manual.** If a Safepay order is paid but the provider fails, the order becomes `needs_attention` and you refund the customer in the Safepay dashboard. Stripe orders are refunded automatically.
- **Currency:** Safepay settles in PKR. Prices are sent in the offer's own currency with no exchange rate applied. If your Safepay account only accepts PKR, an FX conversion step must be added before this is usable.
- Separately from payment, check that you can fund Duffel in USD (it bills your Duffel balance).

## How a purchase works

1. The customer searches (`POST /api/commerce/{flights/search,hotels/search,insurance/quotes}`). Prices come from the provider; our fee (`SERVICE_FEE_PERCENT`) is added on the server.
2. They enter traveller details and click Pay (`POST /api/commerce/checkout`). The server re-prices the offer with the provider and refuses (409) if the total differs from what the customer saw. It stores an **order** (travellers encrypted with `DATA_KEY`) and returns a Stripe Checkout URL.
3. The customer pays on Stripe's hosted page. Card details never touch this server.
4. Stripe calls `POST /api/commerce/webhook` (signature verified). Only then is the provider called to create the real order.
5. Provider succeeded: the order becomes `fulfilled`, with the provider's own booking reference and e-ticket numbers, and a `confirmed` booking (source `provider`) is added to Bookings.
6. Provider failed: the customer is refunded automatically (`refunded`). If the refund itself fails, or the paid amount does not match, or the provider booked but we could not save it, the order becomes `needs_attention` and an `order.needs_attention` audit entry is written.

References and ticket numbers are never generated by TripPilot. A fulfilled order without a provider reference is rejected by the database.

## Setup checklist (test mode first)

1. Run `server/migrations/005_orders.sql` in the Supabase SQL editor (already included in `all.sql`).
2. Stripe (only if you can open an account): create a test key, set `STRIPE_SECRET_KEY`. Add a webhook endpoint `https://<domain>/api/commerce/webhook/stripe` for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired`; set `STRIPE_WEBHOOK_SECRET`.
2b. Safepay: set `SAFEPAY_API_KEY`, `SAFEPAY_SECRET_KEY`, `SAFEPAY_WEBHOOK_SECRET` from the merchant dashboard and add the webhook `https://<domain>/api/commerce/webhook/safepay`. Keep `SAFEPAY_ENV=sandbox` until a test payment works end to end.
3. Duffel: create a test token, set `DUFFEL_ACCESS_TOKEN`. Duffel charges your Duffel **balance**, so top it up before going live. Duffel Stays access must be enabled by Duffel.
4. Make a test purchase with Stripe card `4242 4242 4242 4242`. Check: order reaches `fulfilled`; a Booking appears; a failed provider call refunds.
5. **Verify on Vercel** that the webhook receives the raw request body (signature checks fail if a platform re-serialises JSON). If Stripe shows signature errors, this is the first thing to check.
6. Before live keys: terms of sale and refund policy, a business entity that can take payments, and a check of the Vercel plan (Hobby is non-commercial only).

## Known gaps

- **Insurance works differently from flights and hotels (HelloSafe Atlas).** Atlas can price a trip and mint a tracked link, but its API cannot bind a policy or take a payment. So TripPilot shows live quotes, and "Continue on HelloSafe" opens HelloSafe's own page where the traveller pays. Stripe/Safepay are not involved and there is no TripPilot order. Set `ATLAS_KEY_ID` and `ATLAS_SIGNING_SECRET` (dashboard → API keys). A sandbox key (`ak_test_...`) returns sample prices from a fictional insurer and **purchase links are disabled** because a sandbox link opens HelloSafe's real checkout. Live keys need a short review by HelloSafe. Your commission is tracked by HelloSafe against your partner account, not by this app. The adapter is `server/src/integrations/hellosafe.ts` (quote/link calls follow their published OpenAPI spec; not yet run against a live key).
- **Duffel Stays payment step is unverified** (see the comment in `duffel.ts`). Hotels take the cheapest room rate per property and one lead guest.
- **No self-service cancellation or change.** Refunds after a successful booking are handled by you in Stripe and with the provider.
- **No payment email or receipt** beyond what Stripe and the provider send (the app has no email delivery yet).
- Stripe amounts are minor units; currencies with 0 or 3 decimals are handled, but only USD/EUR-style currencies have been exercised in tests.
